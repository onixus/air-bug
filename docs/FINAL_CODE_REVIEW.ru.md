## 1. Согласованность архитектуры

Единый шаблон на все три машинно-контрактные команды (`aircrack`/offline,
`airdecap`, `survey`):

- `exit.rs` даёт один слой: `Category` → `(код выхода, стабильная метка)`,
  `Diagnostic` (резерв файла + запись JSON), обёртки `run_with_diagnostic[_counts]`.
- Каждая команда следует одному разбиению `run()` (внешняя обёртка) → `execute()`
  (прежняя логика), а `classify()` относит ошибку к категории. Это чистое,
  повторяемое разделение; поведение без `--diagnostic-json` не меняется — файл не
  создаётся, процесс завершается тем же кодом категории.
- Приоритет классификации правильный: сначала типизированные причины
  (`classify_cause` — `Category` в цепочке `anyhow`, `std::io::Error`,
  `air_capture::CaptureError`), и лишь затем — текстовый fallback. Критичные пути
  (`dictionary.rs`, `multi.rs`) уже помечены типизированным `.context(Category::…)`,
  так что не зависят от текста.

Контракт кодов задокументирован в `docs/CLI_MACHINE_CONTRACT.md` и зафиксирован
тестом `codes_and_labels_are_stable_and_distinct` — случайная правка кода/метки
ломает сборку тестов. Нумерация следует `sysexits.h` там, где применимо
(USAGE=64, INTERNAL=70), прочие коды — в непересекающемся диапазоне 2–6.

## 2. Безопасность: отсутствие утечки секретов и путей

Это сильнейшая часть интеграции и проверена наиболее тщательно.

- **Поле `error` в JSON — только статические безопасные строки** из
  `safe_error(category)`. Подробные ошибки (с путями, байтами, текстом от ОС)
  остаются исключительно в stderr. Пароль, PMK, WEP-ключ, PMKID в JSON не попадают
  ни на одном пути — счётчики `Counts` по построению обезличены.
- **Доказано тестами-часовыми.** `machine_contract.rs` прогоняет сентинелы
  `secret-sentinel` в путях, именах, а также реальные секреты (`--pass`, `--pmk`,
  `--wep-key`, `correct horse battery`) через успешные и неуспешные прогоны и
  утверждает, что их нет в выводе JSON. Коллизии экспортов (`survey`, `airdecap`)
  проверяют, что путь temp-каталога не просачивается в диагностику.
- **Создание файла безопасно.** `Diagnostic::reserve` использует
  `create_new(true)` (O_EXCL — не идёт по существующему symlink, не перезаписывает)
  и на Unix ставит `mode(0o600)`. Существующие файлы никогда не затираются; это же
  поведение у диагностики, записанной на пути ошибки аргументов.

## 3. Бюджеты ресурсов

Жёсткие границы сохранены и не ослаблены интеграцией:

- offline/`execute`: ≤64 захватов, ≤64 словарей, ≤256 BSSID, ≤256 сетей —
  явные `bail!` до начала тяжёлой работы; `CaptureLimits`, `max_records`,
  `max_targets` пробрасываются как раньше.
- `airdecap`: `max_capture_mib`, `max_packets` (диапазоны валидируются clap).
- Диагностический JSON ограничен по размеру по конструкции: это маленький объект
  фиксированной схемы (`schema_version`, счётчики, метка), не растущий с размером
  входа.
- SIGINT корректно даёт `Partial` (код 6) с сохранением возобновляемого
  checkpoint — покрыто `sigint_is_partial_and_leaves_resumable_checkpoint` для
  одиночного и multi-путей.

## 4. Кросс-платформенность

- `mode(0o600)` — под `#[cfg(unix)]`; на Windows файл создаётся с ACL по
  умолчанию (см. рекомендацию R3 — не блокер, т.к. секретов в файле нет).
- Остальной код интеграции платформонезависим (`std::fs`, `serde_json`, `anyhow`).
- Прогон clippy и тестов выполнен на darwin — чисто. Кросс-платформенные прогоны
  (Linux/Windows/Android) заявлены в `docs/CROSS_PLATFORM_ACCEPTANCE.ru.md`; на
  этой машине они не перепроверялись (см. ограничения).

## 5. Использование APEX-токенов (этап 4)

- `Palette` вендорит ровно подмножество APEX 0.1.0 (ссылка на источник указана).
  `DARK`/`LIGHT` заданы как RGB-константы.
- Новый тест `palettes_contain_exactly_the_required_apex_tokens` деструктурирует
  `Palette` исчерпывающим паттерном без `..`: добавление, удаление или
  переименование токена становится ошибкой компиляции. Это удачный способ
  зафиксировать контракт набора токенов во времени.
- `Theme::System` определяет светлую тему через `COLORFGBG` с fallback на тёмную —
  поведение задокументировано в CLI и README.

**Ограничение контракта (не дефект):** тест проверяет *наличие* токенов, но не
их значения и не контрастность. Заявление «Apex token/contrast check — PASS» в
документации относится к Android-проверке (`android/tests/check_apex.py`), а не к
TUI-палитре (см. R2).

## 6. Тесты

- Тесты уровня процесса (`machine_contract.rs`) запускают реальный бинарник и
  проверяют код выхода, схему JSON, метку категории, поле `verification` и
  отсутствие секретов — это проверка контракта, а не внутренней реализации, что
  правильно для стабильного внешнего контракта.
- Покрыты распределения категорий: bad_container, privilege_or_device,
  no_supported_target, usage, partial (candidate-limit и SIGINT), internal
  (сбой кэша), password_not_found, success — в одиночном и multi-путях.
- `Temp` с уникальными каталогами на процесс/счётчик и `Drop`-очисткой — тесты
  изолированы и не оставляют мусор.

## Рекомендации

**R1 — Хрупкость текстового fallback в `classify()` (сопровождение, низкая).**
Ветви `classify` в `offline.rs`/`decap.rs`/`survey.rs` сопоставляют подстроки в
нижнем регистре по всей цепочке ошибок. Критичные пути уже типизированы через
`.context(Category::…)`, поэтому на них текст не влияет. Но для нетипизированных
`bail!` переформулировка сообщения способна тихо перевести исход в `Internal`.
Рекомендация: постепенно переводить оставшиеся `bail!` на типизированный
`.context(Category::…)` (как уже сделано в `dictionary.rs`/`multi.rs`), сводя
текстовый fallback к подстраховке. Сейчас это покрыто тестами, так что регрессия
будет замечена для проверяемых сообщений.

**R2 — Контрастность APEX в TUI не проверяется автоматически (низкая).**
Стоит добавить тест, вычисляющий контраст `text_primary`/`text_secondary` к
`bg_canvas`/`surface_*` (WCAG-порог), либо явно указать в документации, что
контрастность TUI-палитры — ручная проверка, чтобы не смешивать её с
Android `check_apex.py`.

**R3 — Права диагностического файла на Windows (информативно).**
`mode(0o600)` только под `unix`. Файл секретов не содержит, поэтому это не риск
утечки, но стоит одной строкой зафиксировать в `CLI_MACHINE_CONTRACT.md`, что
приватные права гарантируются только на Unix.

**R4 — Дублирование разбора аргументов на пути ошибки clap (низкая).**
В `main.rs` при неуспешном `try_parse()` argv сканируется вручную, чтобы найти
`--diagnostic-json`/`--json` и всё же записать диагностику категории `usage`.
Логика расходится с парсером clap (ручной разбор `=` и ведущего `-`). Поведение
задокументировано и покрыто `argument_error_diagnostics_support_hyphen_paths`, но
это точка возможного расхождения при будущих правках флагов — стоит оставить
рядом комментарий-предупреждение и держать тест.

**R5 — Зафиксировать статус слияния.** Перед закрытием PR убедиться, что ветки
сливаются по порядку (stage1 → stage4 → stage5 → stage6) либо вливается вершина
stage6: `main` сейчас не содержит ни кода, ни тестов интеграции.
