# Code review: риски и пробелы интеграции aircrack-rs в Shapoclyack

Обзор существующего кода с точки зрения встраивания в EASM/RBVM-платформу.
Без изменений исходников; это заметки для планирования (см.
[ROADMAP](ROADMAP_INTEGRATION.ru.md) и [архитектуру](INTEGRATION_ARCHITECTURE.ru.md)).
Опора: [ARCHITECTURE.md](../ARCHITECTURE.md), [README.md](../README.md),
[SECURITY.md](../SECURITY.md), [AUDIT.md](AUDIT.md).

Градация: **[B]** блокер интеграции, **[H]** высокий, **[M]** средний, **[L]** низкий.

## 1. Контракты и совместимость

- **[B] Нет стабильных машинных exit codes / единого диагностического JSON.**
  `air-cli` возвращает `anyhow::Result`, диагностика идёт человекочитаемым текстом
  в stderr. Backend не может надёжно отличать «пароль не найден», «нет
  поддерживаемой цели», «повреждённый контейнер», «ошибка привилегий» по коду
  возврата. Пробел уже отмечен в ARCHITECTURE («стабильные машинные диагностики и
  exit codes» в приоритетах). → `shapo-ingest` до этого обязан опираться на
  JSON-файл экспорта, а не на парсинг stdout/stderr.
- **[M] Версионирование форматов.** Survey JSON — `schema_version: 1`; JNI JSON
  хранит legacy-поле `sessions` для совместимости; checkpoint дошёл до v6. Это
  хорошо, но контракт с backend должен явно пинить мажорную версию и отклонять
  неизвестную, а не читать поля оптимистично.
- **[M] CSV небезопасен как единственный источник.** Теряет pending-cache/coverage
  диагностику; для RBVM-полноты нужен JSON. CSV — только для ручного экспорта.
- **[L] Неподдерживаемые команды.** `aireplay/airbase/packetforge/ivstools/airmon`
  дают unsupported-ошибку. Backend не должен их вызывать; задокументировать в
  ingest-слое список разрешённых подкоманд.

## 2. Безопасность

- **[B] Привилегии capture.** `live`/`survey` требуют системный tcpdump и доступ к
  capture-устройству; monitor mode может отключить Wi-Fi/дисассоциировать (на
  macOS доступ к `/dev/bpf0` этому пользователю был запрещён). Эти привилегии
  нельзя давать backend. → Изолировать в `shapo-sensor`/CLI-процессе; backend
  получает только файлы-результаты.
- **[H] Найденный пароль и PMK — секреты.** `aircrack` печатает пароль в stdout;
  `air-crack::cache` хранит PMK и candidate-hash (не plaintext, но чувствительно);
  cache — «не encrypted vault». → verification-ветвь не должна течь в backend/логи;
  результат слабого PSK передавать как факт «weak credential» + ссылку на артефакт,
  не сам пароль. Канал сенсор→backend — mutual TLS; буфер на диске 0600.
- **[H] Авторизация цели.** Код не навязывает подтверждение владельца сети —
  это процедурное требование (README/Android UI напоминают). → Authorization gate
  обязателен в сенсоре и в UI до любого радио-действия; фиксировать в аудит-логе.
- **[M] Обнуление секретов не гарантировано.** ARCHITECTURE прямо указывает: zeroize
  секретов и формальный крипто-аудит не гарантированы; на Android строки нельзя
  надёжно занулить в Java heap. → Не хранить секреты в долгоживущих процессах
  backend; помечать хосты верификации как доверенные.
- **[M] PCAP содержит исходные пакеты.** Survey-audit не хранит идентичности/EAP,
  но сохранённый PCAP содержит оригинальный трафик. → Классифицировать PCAP как
  чувствительный артефакт в Shapoclyack, 0600, контроль доступа, срок хранения.
- **[L] Процесс-контроль.** `shadow` не сигналит произвольному PID (хорошо), но
  SIGKILL/краш supervisor может оставить дочерний процесс; stale lock снимается
  вручную. → Сенсор должен детектить осиротевшие процессы/локи при старте.

## 3. Ресурсные лимиты

- **[H] Offline desktop CLI не имеет общего memory/CPU sandbox.** ARCHITECTURE:
  «это не OS RSS/CPU sandbox»; desktop extraction может строить декартово
  произведение кандидатов (bounded до 1024×1024, но вычислительно дорого).
  Android/JNI лимиты (4 MiB/16 MiB/32768/128) на desktop не распространяются. →
  Для автоматической телеметрии использовать bounded `survey`, а не произвольный
  `aircrack`; verification запускать с явными `--max-*` и в ограниченном cgroup/
  контейнере на стороне сенсора.
- **[M] Враждебный capture.** Парсер bounded (buffer 8 MB, ≤256 интерфейсов,
  ≤4096 строк таблиц, expiry), но входной PCAP может быть атакующим. → Сенсор
  принимает capture только из доверенного собственного tcpdump; загрузку внешних
  PCAP в верификацию — через bounded-флаги и изолированный процесс.
- **[L] Нет disk rotation в live.** Default 300 c / 100000 пакетов, без ротации. →
  Ротация/квоты — ответственность сенсора.

## 4. Кроссплатформенность

- **[B] Windows: нет live-capture.** Offline-портируемо, live-пути только
  Linux/macOS. → На Windows агент — только offline + потребитель UI/телеметрии.
- **[H] macOS radio-приёмка ограничена.** Продакшн-`survey` отказывает на
  ассоциированном адаптере до открытия BPF; реальное радио на тестовом Mac не
  прошло полную приёмку; дисассоциация прерывает связь. → macOS-сенсор
  позиционировать как ограниченный/ручной, не как постоянный автоматический.
- **[M] Android — только offline.** Нет live/monitor/root/injection; APK без сети.
  Device-приёмка подтверждена частично (NativeSmokeTest на реальном телефоне;
  UI-темы — с замечанием по контрасту статус-бара). → Android = мобильный offline-
  верификатор/просмотрщик, доставка на backend — функция сенсора.
- **[M] Зависимость от внешних бинарей.** `survey`/`live` зависят от системного
  tcpdump; каналы — от `iw` (Linux) и CoreWLAN helper (macOS). → Сенсор проверяет
  наличие/версию зависимостей при старте и сообщает в backend как часть health.
- **[L] Реальное радио/аппаратная совместимость не подтверждены** в ряде отчётов
  (synthetic/VM virtual Ethernet). → Не обещать покрытие драйверов в SLA EASM до
  авторизованной аппаратной приёмки.

## 5. UI / APEX

- **[M] Нет токена severity.** Палитра #117 имеет `success/success_subtle`, но не
  шкалу критичности. Для RBVM severity (крит/высокий/…) нужны либо нецветовые
  средства (текст/иконка/порядок), либо расширение токенов в upstream #117.
  Локально новые токены не вводить (ограничение задачи). → severity кодировать
  нецветом до решения на стороне дизайн-системы.
- **[L] Контраст статус-бара на Android (dark).** Отмечен визуальный дефект
  контраста часов/иконок статус-бара на тёмной теме; контент приложения проходит.
  → Учесть при доведении нативного UI.
- **[L] Нативного macOS GUI нет.** Только TUI; GUI — отдельная работа, должен
  переиспользовать токены #117 и процесс-контракт CLI.

## 6. Эксплуатационные пробелы для EASM/RBVM

- **[M] Нет встроенного маппинга «наблюдение → риск».** Модуль даёт факты
  (open/Privacy/RSN/PMF/evidence-флаги), но не классифицирует их в severity. →
  Правила скоринга живут в `shapo-ingest`/RBVM, не в модуле; модуль остаётся
  источником объективных наблюдений.
- **[M] Evidence-флаги не доказывают эксплуатируемость.** `HS`/`PMKID` — только
  структурный признак; MIC/пароль не проверены; malformed capture может содержать
  правдоподобное evidence. → В UI/ingest явно различать «обнаружено evidence» и
  «подтверждён слабый пароль» (через verification-ветвь).
- **[L] Processing-time vs capture-time.** Возраст/expiry в survey — processing
  time. → Нормализовать временные метки в backend к абсолютному времени сенсора.

## Вывод
Код пригоден как пассивный EASM-сенсор и offline-верификатор при соблюдении:
изоляции привилегий в сенсоре, ручного запуска verification-ветви, строгого
обращения с секретами/PCAP, bounded-лимитов и честного разделения «наблюдение ≠
доказательство». Блокеры до продакшн-интеграции — стабильные exit codes/
диагностический JSON (контракт), изоляция capture-привилегий, и явный отказ от
live на Windows.

## 7. Ревью этапа 1: exit codes и диагностический JSON (2026-10-28)

Объект: незакоммиченные изменения поверх `ec3b692` — `crates/air-cli/src/exit.rs`
(новый), `main.rs`, `offline.rs`, `decap.rs`, `survey.rs`, тесты
`tests/machine_contract.rs`, `tests/decap.rs`, `tests/survey.rs`,
[CLI_MACHINE_CONTRACT.md](CLI_MACHINE_CONTRACT.md), README. Исходники не менялись.

**Проверено:** `cargo fmt --all -- --check` — чисто; `cargo clippy -p air-cli
--all-targets -- -D warnings` — без предупреждений; `cargo test -p air-cli` — все
наборы зелёные (117 тестов). Дополнительно — ручные прогоны
`target/debug/aircrack` на граничных случаях (результаты ниже, помечены
«воспроизведено»).

**Что сделано хорошо.** Коды зафиксированы константами и юнит-тестом на
стабильность/уникальность; `create_new` + 0600 исключает перезапись и symlink-
подмену; путь резервируется до начала работы; для `aircrack`/`airdecap` в `error`

пути не попадают в JSON — покрыто тестами с sentinel-секретами); неуспешный decode

### 7.1 Корректность классификации

- **[H] `survey`: ошибка разбора аргументов даёт код 2 = `password_not_found`.**
  `main.rs:155-189` переводит clap-ошибки в 64 только для `aircrack`/`airdecap`;
  для `survey` остаётся `error.exit()` → clap-код 2, и диагностика не создаётся,
  хотя у `survey` есть `--diagnostic-json`, а help флага обещает «exit category is
  also the process exit code». Воспроизведено: `survey --bogus-flag
  --diagnostic-json X` → rc=2, файла нет. Код 2 совпадает с `PASSWORD_NOT_FOUND`
  → backend ошибочно классифицирует исход. → Включить `survey` в ветку usage (64),
  либо глобально переопределить clap-код ошибок на 64 для всех подкоманд.
- **[H] Остановка по `--max-candidates` / SIGINT классифицируется как `usage`
  (64).** `dictionary.rs:323` — «verification paused …», `offline.rs:143-144`
  матчит `checkpoint`/`paused` → Usage. Воспроизведено: `--max-candidates 5` →
  rc=64. Это штатная частичная проверка (resumable), а не ошибка аргументов;
  backend отбросит её как «неверный вызов». Заодно `PMK cache batch failed;
  checkpoint not advanced` (`dictionary.rs:357`) уходит в Usage, хотя это
  внутренний/IO-сбой. → Отдельная категория (например, `interrupted`/`partial`,
  новый код вне 2–5/64/70), матчинг `checkpoint` убрать.
- **[M] Невалидный UTF-8 в словаре → `bad_container` (4).** `classify_cause`
  (`exit.rs:199-215`) любую `io::Error` с `InvalidData` относит к контейнеру
  захвата; чтение словаря (`dictionary.rs:332`) возвращает именно её.
  Воспроизведено: rc=4, `"cannot read capture: malformed or unsupported
  container"` — неверно указывает на capture. → Типизировать источник (обёртка
  ошибки для wordlist/capture) или проверять `CaptureError` раньше общей `io`.
- **[M] Отсутствующий словарь → `privilege_or_device` (5), ветка
  `has("cannot open wordlist")` → Usage недостижима**, т.к. `classify_cause`
  срабатывает первым на `NotFound`. Воспроизведено: rc=5. То же для отсутствующей
  capture (rc=5). Нужно решение: «нет входного файла» — это usage или device?
  Зафиксировать в контракте и убрать мёртвую ветку.
- **[M] `survey`: коллизия export-файла → `internal` (70) и не использует
  `classify_cause`.** Сообщение `cannot create export …: File exists`
  (`survey_export`) не совпадает с `already exists`/`refusing to overwrite`
  (`survey.rs:113`). Воспроизведено: rc=70. В `airdecap` аналогичная коллизия —
  5. → Привести survey к `classify_cause` и общим правилам; одна и та же причина
  должна давать один код во всех командах.
- **[M] Классификация подстрокой по тексту, включающему пользовательские
  значения.** Цепочки содержат пути/имена интерфейсов; правила вида `has("must")`,
  `has("invalid")`, `has("exceeded")`, а в survey `has("pcap")`/`has("channel")`/
  `has("device")` (`survey.rs:115-125`) зависят от этих значений и от порядка
  веток. Пример по коду: в survey ошибка создания `--output cap.pcap` с
  `Permission denied` попадёт в `bad_container` раньше ветки `permission`.
  Любая правка текста ошибки молча меняет код выхода — тесты ловят только
  покрытые случаи. → Перейти на типизированные ошибки (enum/`thiserror` +
  `downcast_ref`) в точке `bail!`; подстроки — только как временный fallback.
- **[L] Лимиты (`capture byte limit exceeded`, `network limit exceeded`,
  `SSID discovery limit exceeded`) → `usage`.** Допустимо, но backend не отличит
  «превышен ресурсный лимит на враждебном/большом входе» от опечатки во флаге.
  → Рассмотреть категорию `limit_exceeded` или явно задокументировать.
- **[L] `capture changed between discovery and evidence collection` → `internal`.**
  Скорее гонка входа (`bad_container`/отдельная), стоит зафиксировать.

### 7.2 Безопасность и утечки

- **[M] `survey` пишет в JSON сырую цепочку ошибок (`format!("{e:#}")`,
  `exit.rs:179-185`).** Воспроизведено: `"error": "cannot create export
  /var/folders/…/out.json; …"` — абсолютные пути, имена интерфейсов, системные
  сообщения. Секретов PSK в survey нет, но это противоречит принципу контракта
  («no input paths or raw error chains») и уходит в backend/логи. → Единая
  политика: обобщённая фраза для всех команд, детали — только в stderr.
- **[L] Режим редактирования выбирается сравнением строки `kind`**
  (`matches!(kind, "aircrack_diagnostic" | "airdecap_diagnostic")`). Новая команда
  с иным `kind` по умолчанию получит небезопасный путь. → Сделать безопасный
  режим по умолчанию (параметр/enum), а raw-текст — явным opt-in.
- **[L] Windows: 0600 не применяется**, файл наследует ACL каталога. Для
  сенсора на Windows (только offline) — документировать требование приватного
  каталога.
- **[L] Пустой зарезервированный файл при аварийном завершении** (SIGKILL, паника
  с `panic=abort`). Контракт это оговаривает; ingest должен трактовать 0 байт /
  невалидный JSON как `internal`, а не как отсутствие данных. Запись через
  временный файл + `rename` не применима из-за `create_new`-резервации — оставить
  как есть, но добавить тест на пустой файл в ingest.
- Положительно: `--results-json` (с паролем) отделён от диагностики; тесты
  проверяют отсутствие passphrase/PMK/WEP-ключа и sentinel-строки во всех
  ветках `aircrack`/`airdecap`.

### 7.3 Контракт и API

- **[H] `success` у `aircrack` не различает «пароль найден» и «только инспекция
  без словаря».** Воспроизведено: запуск без `--wordlist` → rc=0, JSON без поля
  исхода верификации. Для RBVM ключевой факт — «weak credential подтверждён»
  (§2, §6). → Добавить несекретное поле, например `verification: "found" |
  "not_found" | "not_attempted" | "partial"` (и/или `found_networks: N`) — без
  самого пароля.
- **[M] `survey` вне документа контракта.** `CLI_MACHINE_CONTRACT.md` описывает
  только `aircrack`/`airdecap`, а README ссылается на него обобщённо; у survey
  другой набор полей `counts`, нет алиаса `--json`, иные правила `error`. →
  Добавить раздел survey (или явно пометить его диагностику как
  нестабильную/experimental).
- **[L] Семантика `counts.handshakes` в survey** — число AP с любым
  рукопожатием, а не число рукопожатий; `pmkid` — число AP. Переименовать
  (`aps_with_handshake`, `aps_with_pmkid`) до фиксации schema v1 или описать.
- **[L] `survey` при неуспехе пишет нулевые счётчики** (`run_with_diagnostic`,
  а не `_counts`), напр. «no 802.11 packets received» теряет `packets`. В
  offline-командах это уже решено — выровнять.
- **[L] Самодельный пре-скан `--json` в `main.rs:162-178`** дублирует clap и
  может создать файл по значению, предназначавшемуся другому флагу при
  синтаксически битой строке. Риск мал (create_new, 0600); упростить, если
  перейти на глобальный перехват clap-ошибок.
- **[L] Код 1** (anyhow-ошибка из `main` для прочих подкоманд) и **код 2**
  (clap) остаются вне контракта. Задокументировать: «коды вне таблицы —
  `internal`/неподдержанная команда».
