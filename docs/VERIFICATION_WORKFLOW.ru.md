# Ручная изолированная верификация для Shapoclyack

Этап 5 [roadmap интеграции](ROADMAP_INTEGRATION.ru.md): оператор проверяет
кандидаты PSK по разрешённому PCAP, а Shapoclyack получает факт и доказательную
ссылку для RBVM. Это регламент оркестрации поверх существующего CLI;
контейнерный runner, API запуска и ingest этим документом не реализованы.
Машинные исходы определяет [CLI machine contract](CLI_MACHINE_CONTRACT.md).

## 1. Кто и когда запускает задачу

Верификация запускается **только по явной команде оператора** с правами на
конкретный tenant и актив. Наличие HS/FT/PMKID, новый survey-снимок, событие
очереди, расписание, AI-рекомендация или рост severity не запускают подбор.
Backend может хранить запрос и показывать результат, но не инициирует задачу
самостоятельно. Повтор, расширение словаря, увеличение бюджета и resume требуют
новой команды оператора; автоматического retry подбора нет.

До запуска оператор фиксирует:

- разрешение владельца, tenant, `asset_id`, точный BSSID и байты SSID;
- `run_id`, свою идентичность, время и границы разрешённой проверки;
- `evidence_id`, происхождение PCAP, SHA-256 и время захвата;
- версию/хеш CLI или digest образа, идентификатор и версию локального словаря;
- лимиты, срок хранения, ответственного и условия остановки.

Принадлежность актива проверяют отдельно: совпадение имени SSID не доказывает
владение сетью. Соседние BSSID и другие tenant не входят в scope. Если scope,
разрешение, происхождение или привязка PCAP неоднозначны, запуск отклоняют.
Строки SSID, пути и параметры из PCAP не превращают в shell-команду: runner
передаёт разрешённые аргументы массивом, без shell-интерполяции.

## 2. Граница изоляции и ресурсы

Одна задача — один временный непривилегированный контейнер/VM. Backend и
пассивный сенсор не являются средой подбора. Для offline-задачи не нужны радио,
monitor mode, root, host network, Docker socket или системные устройства.
Пример обязательного профиля Linux runner:

| Ресурс/доступ | Ограничение одной задачи |
| --- | --- |
| Сеть | Полностью отключена; доставка результата отдельным доверенным процессом |
| Привилегии | Отдельный UID, без capabilities, `no-new-privileges` |
| Файловая система | Корень read-only; только выбранные PCAP/словарь read-only; приватный output |
| Память | cgroup: 512 MiB, без дополнительного swap; OOM фиксируется как незавершённость |
| CPU | cgroup: 1 CPU; CLI `--threads 1` |
| Процессы | Не более 32 PID; остановка всей группы/контейнера |
| Время | Watchdog 300 s wall-clock; затем SIGTERM, через 10 s SIGKILL |
| Диск | Output/tmp с квотой 64 MiB; ограничение размера и количества входных файлов |
| Параллелизм | Одна задача на worker; отдельная квота очереди на tenant |

Это пример бюджета, который оператор утверждает до запуска. Проверка
применения cgroup, квот и watchdog обязательна; при недоступности механизма
задачу не запускают. Ограничение CPU-потоков или логический профиль сами по себе
не обеспечивают изоляцию. На macOS/Windows используют среду с эквивалентными
лимитами, например Linux VM; наличие CLI не подтверждает эти гарантии.

CLI дополнительно ограничивает объём работы:

| Флаг `aircrack aircrack` | Пример | Что ограничивает |
| --- | --- | --- |
| `--max-capture-mib` | `64` | Бюджет входного capture в MiB, не RSS процесса |
| `--max-packets` | `100000` | Число обрабатываемых пакетов |
| `--max-records` | `128` | Релевантные EAPOL/association records перед pairing |
| `--max-targets` | `16` | Извлечённые цели верификации |
| `--max-candidates` | `10000` | Дополнительные строки словаря в этом запуске |
| `--threads` | `1` | Число Rayon workers |

`--max-candidates` не ограничивает секунды; `--max-capture-mib` не заменяет
лимит памяти. Чтение/хеширование входов тоже входит в watchdog. Не полагаются
на большие CLI defaults; для простого учёта бюджета выбирают один PCAP, один
BSSID и один обычный файл словаря. Достижение лимита не означает отрицательный
результат проверки. У `airdecap` есть `--max-capture-mib` и `--max-packets`,
но нет `--max-candidates`, `--max-records`, `--max-targets` или `--threads`.

## 3. Выполнение внутри подготовленной среды

Доверенный runner проверяет разрешение и хеши, монтирует только разрешённые
входы, создаёт новый output-каталог 0700 и включает лимиты из раздела 2.
Следующая команда — **только внутренний шаг**, она сама не создаёт sandbox,
cgroup или watchdog. Пути и SSID/BSSID здесь иллюстративные:

```sh
umask 077
set +x
aircrack aircrack \
  --capture /input/authorized.pcap \
  --wordlist /input/approved-words.txt \
  --essid 'Authorized-Lab' --bssid 02:00:00:00:01:01 \
  --max-capture-mib 64 --max-packets 100000 \
  --max-records 128 --max-targets 16 --max-candidates 10000 \
  --threads 1 --diagnostic-json /output/diagnostic.json \
  </dev/null >/dev/null 2>/dev/null
verification_exit=$?
# Runner сохраняет verification_exit как число, без вывода потоков CLI.
```

Runner должен получить настоящий exit code даже при неуспехе команды
(не оборвать обработку через `set -e`). Путь диагностики должен быть новым:
CLI не перезаписывает существующие файлы и symlink. Нельзя использовать pipe
в `tee`, общий job log или парсить `[+] found` из stdout. Даже при отсутствии
`--results-json` stdout может содержать найденный пароль/PMK, а stderr —
подробности ошибок и пути. Потоки подавляют у дочернего процесса до запуска;
их не пересылают в логи контейнера, CI, APM или backend.

После завершения доверенный процесс проверяет целостность JSON, версию схемы,
`command=aircrack`, `kind=aircrack_diagnostic`, согласованность exit code и
категории. Для положительного результата требуется одновременно код `0`,
`exit_category=success`, `verification=found` и подтверждённая привязка задачи
к одному разрешённому BSSID. Инспекция без `--wordlist` тоже может вернуть `0`,
но её `verification=not_attempted` не является верификацией.

| Исход | Интерпретация в workflow |
| --- | --- |
| `0`, `found` | Кандидат подтвердился для выбранной сети; классификация зависит от метода |
| `2`, `not_found` | Словарь исчерпан; сильный пароль и отсутствие риска не доказаны |
| `3`, `no_supported_target` | Нет пригодной поддержанной цели; эксплуатируемость неизвестна |
| `4`, `bad_container` | Повреждённый/неподдержанный capture; нужна проверка входа |
| `5`, `privilege_or_device` | Ошибка доступа/вывода; результата верификации нет |
| `6`, `partial` | Лимит кандидатов или обработанный сигнал; задача не завершена |
| `64`, `usage` | Ошибка аргументов/словаря, в том числе capture/resource limits по текущему контракту |
| `70`, `internal` | Сбой выполнения/диагностики; положительного вывода нет |
| Timeout, OOM, SIGKILL, отсутствующий/неполный JSON | Незавершённый запуск с причиной от runner |

Неизвестная версия схемы, несовпадение кода с JSON или чужой `run_id` блокируют
импорт результата. JSON не содержит `run_id`: связь обеспечивает runner через
уникальный каталог и сохранённый манифест задачи. `not_found`/`partial` в
многосетевом режиме могут включать отдельные совпадения; этот регламент
использует один BSSID и не делает per-network выводов из общей сводки.

## 4. Секреты и чувствительные артефакты

Пароли, кандидаты, PMK/PTK и иные ключи не отправляются в backend, RBVM,
общие логи, тикеты, аналитику или AI-контекст. Нельзя передавать даже хеш
найденного пароля: слабые кандидаты можно перебрать. `--results-json`
содержит кандидаты и в обычной задаче запрещён. `--pmk-cache` выключен:
кэш хранит PMK и идентификаторы кандидатов, это не зашифрованное хранилище.
Checkpoint `--session`/`--resume` не содержит пароль/PMK, но остаётся приватным;
resume возможен только после новой команды оператора с теми же входами.
Core dumps отключают; swap, snapshots и диагностические дампы среды не должны
сохранять память с ключами.

PCAP/PCAPNG — **чувствительные доказательства**, даже если в них нет plaintext
пароля: EAPOL/PMKID допускают offline-проверку, кадры содержат адреса и payload.
Очищенный `wpaclean` capture также остаётся чувствительным. Требования:

- файлы 0600, каталоги 0700 на Unix; эквивалентные закрытые ACL на Windows;
- tenant isolation, доступ по ролям, аудит каждого чтения/экспорта;
- шифрование хранения и разрешённой передачи, отдельное защищённое хранилище
  внутри доверенного периметра; в backend по умолчанию только непрозрачная ссылка;
- срок удаления задаётся до запуска, например 7 суток по локальной политике;
  удаление охватывает копии, временные файлы и snapshots с учётом legal hold;
- запрет публичных bucket, PR-вложений и CI artifacts с реальными capture.

`airdecap` допустим только как отдельный явно разрешённый шаг. Успех расшифровки
с известным сильным ключом не доказывает слабый PSK; open-traffic decode вообще
не проверяет ключ. Его `--pass`/`--pmk` передают секрет через argv, поэтому
использование возможно лишь в среде без постороннего доступа к списку процессов
и записи команд/exec telemetry. Пока такой границы нет, шаг не выполняют.
Расшифрованный PCAP содержит plaintext и требует ещё более строгого доступа;
его payload не импортируют в backend. Для сигнала weak credential расшифровка
не требуется. SAE/FT-SAE с предоставленным PMK подтверждает применимость ключа,
а не возможность пассивного подбора пароля WPA3.

## 5. Передача результата и severity в RBVM

Доверенный адаптер формирует пакет по allowlist: tenant, `asset_id`, `run_id`,
`evidence_id`, оператор/разрешение, времена, BSSID, версия инструмента, метод,
идентификатор утверждённого словаря, бюджеты, exit code/category,
`verification`, безопасные счётчики, SHA-256 PCAP и защищённая ссылка на него.
Это требования к будущему адаптеру, не новая схема CLI. Не копируют произвольные
поля JSON и тексты ошибок; не включают ключи, кандидаты, raw stdout/stderr,
локальные секретные пути, EAPOL/nonce/MIC или payload.

Только подтверждённый PSK из утверждённого словаря слабых кандидатов даёт сигнал
`weak credential`: «кандидат совпал с MIC/PMKID для разрешённого BSSID при
указанном методе и бюджете». Использование словаря известных ключей или
предоставленного PMK описывают как проверку ключа, без вывода о его слабости.
HS/FT/PMKID из survey остаются структурными наблюдениями.

Severity назначает **RBVM Shapoclyack**, не `aircrack-rs`. Подтверждённый weak
credential повышает severity относительно неподтверждённого наблюдения по
утверждённому правилу RBVM с учётом критичности актива и доступного сегмента.
Например, правило может повысить оценку до High для корпоративного PSK;
это пример политики, не фиксированная оценка CLI и не автоматически Critical.
Сохраняют предыдущее/новое значение, версию правила, обоснование, время и
evidence-ссылку. Повторный импорт одного `run_id` не создаёт дубликат finding.

Совпадение доказывает проверку кандидата по capture, но не подключение к сети,
компрометацию устройства или доступ к данным. `not_found`, лимиты и ошибки
не понижают severity и не закрывают finding автоматически. После смены PSK
оператор отдельно разрешает retest по новому capture; результат старого capture
не подтверждает устранение текущего риска.

## 6. Приёмка оркестрации перед эксплуатацией

На синтетических данных оператор и reviewer проверяют:

- событие survey/очереди без команды оператора не запускает задачу;
  неверный tenant/BSSID/истёкшее разрешение отклоняются;
- реально действуют ограничения CPU/RAM/PID/диска/времени и запрет сети;
  timeout/OOM останавливают все дочерние процессы без автоматического retry;
- известный слабый кандидат даёт `found`, неверный словарь — `not_found`,
  inspection — `not_attempted`, кандидатный лимит — `partial`;
- пароль и PMK с тестовыми маркерами отсутствуют во всём пакете backend,
  логах, трассировках и артефактах общего доступа;
- повреждённый JSON, несогласованные коды, неизвестная схема и подмена PCAP
  не дают положительного сигнала; чтение чужого evidence запрещено;
- RBVM хранит изменение severity с evidence и версией правила; повторный
  импорт идемпотентен, отрицательный результат не закрывает риск;
- по истечении retention удаляются временные входы/выходы и приватные копии.

Это критерии будущей реализации runner/ingest. Наличие документа или успешный
локальный CLI-тест не означает, что изоляция и интеграция Shapoclyack уже
проверены в эксплуатации.
