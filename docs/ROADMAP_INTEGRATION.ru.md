# Roadmap интеграции aircrack-rs в Shapoclyack (EASM/RBVM) + APEX

Поэтапный план с критериями приёмки. Опора: [архитектура интеграции](INTEGRATION_ARCHITECTURE.ru.md),
[code review](CODE_REVIEW_INTEGRATION.ru.md), [ARCHITECTURE.md](../ARCHITECTURE.md),
[README.md](../README.md). Каждый этап самодостаточен и проверяем; этапы
упорядочены по зависимостям (контракт → сенсор → UI → верификация → аппаратура).

Статусы приёмки: формулируются как проверяемые утверждения, а не как намерения.
«Выполнено» означает прошедшую проверку, а не наличие кода/CI-workflow.

---

## Этап 0 — Базовая линия и границы (документы)
**Цель:** зафиксировать, что переиспользуется как есть и что строится рядом.

Работы:
- Утвердить список повторно используемых крейтов и контрактов (§2, §4 архитектуры).
- Зафиксировать список разрешённых подкоманд CLI для backend; запрет вызова
  неподдерживаемых (`aireplay`/`airbase`/`packetforge`/`ivstools`/`airmon`).

Критерии приёмки:
- [ ] Контракт survey-JSON (`schema_version: 1`) описан полями и зафиксирован как
      единственный источник телеметрии для backend.
- [ ] Перечень разрешённых/запрещённых подкоманд согласован с командой Shapoclyack.
- [ ] Исходники `aircrack-rs` не изменены (только docs/внешний слой).

## Этап 1 — Стабильный машинный контракт (CLI exit codes + диагностический JSON)
**Цель:** backend различает исходы без парсинга текста. Закрывает блокер
[CODE_REVIEW §1](CODE_REVIEW_INTEGRATION.ru.md).

Работы (в будущем — отдельное изменение кода `air-cli`, вне текущей задачи-докумен-
тации): стабильные exit codes и опциональный `--json` диагностический поток для
`survey`/`aircrack`/`airdecap`. До него — ingest читает JSON-файл экспорта.

Критерии приёмки:
- [ ] Для `survey` экспорта задокументировано, что успех определяется наличием и
      валидностью JSON `schema_version: 1`, а не текстом stdout.
- [ ] Определены коды/категории исходов: успех, пароль не найден, нет поддержанной
      цели, повреждённый контейнер, ошибка привилегий/устройства.
- [ ] `shapo-ingest` отклоняет неизвестную мажорную версию схемы, а не угадывает поля.
- [ ] Контрактные тесты на синтетических captures подтверждают стабильность полей
      JSON между запусками.

## Этап 2 — Сенсор-агент `shapo-sensor` (Linux, пассивная телеметрия)
**Цель:** непрерывная EASM-телеметрия из `survey` с изоляцией привилегий.

Работы: обёртка над `air-cli survey`, authorization gate, троттлинг снимков,
локальный буфер 0600 с ротацией, доставка на `shapo-ingest` по mutual TLS.

Критерии приёмки:
- [ ] Агент не запускается без конфига с разрешённым интерфейсом (и BSSID для live);
      отказ логируется.
- [ ] Привилегии capture присутствуют только у дочернего CLI-процесса; агент/канал
      доставки их не требуют.
- [ ] Снимки survey-JSON доставляются идемпотентно (`sensor_id`+timestamp); при
      недоступности backend буферизуются локально без потери bounded-гарантий.
- [ ] Канал — взаимно аутентифицированный TLS; PCAP не передаётся без явного запроса.
- [ ] Осиротевшие процессы/stale-локи детектируются при старте.
- [ ] Прогон на Linux-сенсоре с authorized capture даёт корректный JSON в backend.

## Этап 3 — Приём и нормализация в Shapoclyack (`shapo-ingest` + EASM/RBVM)
**Цель:** превратить наблюдения в ассеты EASM и risk-signals RBVM.

Работы: разбор survey-JSON → беспроводные ассеты (BSSID/SSID/канал/защита),
нормализация времени к абсолютному, маппинг наблюдений в severity (правила в RBVM,
не в модуле), различение «evidence обнаружено» vs «эксплуатируемость подтверждена».

Критерии приёмки:
- [ ] AP/клиенты становятся ассетами EASM с сохранением `ssid_hex` и меток защиты.
- [ ] Risk-signals (open, Privacy/возможный WEP, нет PMF, слабые AKM/шифр,
      Enterprise-метаданные, evidence-флаги) формируются только из полей JSON.
- [ ] Severity-классификация живёт в ingest/RBVM; модуль не изменён.
- [ ] UI/данные явно различают «evidence обнаружено» и «слабый пароль подтверждён».
- [ ] Processing-time приведён к абсолютному времени сенсора.

## Этап 4 — UI поверх APEX (TUI + web + Android/macOS потребитель)
**Цель:** единый визуальный язык только на существующих токенах #117.

Работы: дашборд survey (TUI уже есть в `air-tui`), виджеты EASM в web-UI
Shapoclyack, Android/macOS как потребители телеметрии и offline-верификаторы.

Критерии приёмки:
- [ ] Используются только токены из `apex_tokens.rs` / `ApexTokens.java`
      (`bg_canvas`, `surface_1/2`, `border_control`, `text_primary/secondary`,
      `accent`, `focus_ring`, `success`, `success_subtle`). Новых токенов нет.
- [ ] Severity кодируется нецветовыми средствами (текст/иконка/порядок) до любого
      решения о расширении токенов в upstream #117.
- [ ] Один `accent` на экран; фокус — `focus_ring` (2dp на Android).
- [ ] Контраст проходит порог Apex-проверки (текст ≥4.5:1, control/focus ≥3:1);
      `android/tests/check_apex.py` зелёный.
- [ ] Темы Dark/Light/System работают в TUI и Android; macOS GUI (если делается)
      переиспользует те же токены и процесс-контракт CLI.
- [ ] UI показывает ограничения: evidence ≠ проверка пароля, `?` = не наблюдалось,
      security-метка = реклама AP.

## Этап 5 — Ветвь верификации (ручная, изолированная)
**Цель:** подтверждать эксплуатируемость слабого PSK как сигнал RBVM, безопасно.

Работы: оркестрация `aircrack`/`airdecap` по явной команде оператора, в
ограниченном контейнере/cgroup, с bounded `--max-*`; результат — факт «weak
credential» + ссылка на артефакт, без утечки пароля/PMK в backend.

Критерии приёмки:
- [ ] Верификация запускается только вручную оператором, не автоматически из backend.
- [ ] Процесс ограничен ресурсами (память/CPU/время) и bounded-флагами CLI.
- [ ] Найденный пароль/PMK не попадают в backend/логи; передаётся статус и метаданные.
- [ ] Исходный PCAP классифицирован как чувствительный (0600, контроль доступа,
      срок хранения).
- [ ] Результат в RBVM повышает severity актива с явным обоснованием-доказательством.

## Этап 6 — Кроссплатформенная и аппаратная приёмка
**Цель:** честные границы покрытия по ОС и радио.

Критерии приёмки:
- [ ] Windows: агент работает только offline (разбор PCAP + потребитель UI); live
      явно недоступен и так помечен.
- [ ] Linux: авторизованный аппаратный passive-capture подтверждён на реальном
      адаптере (отдельно от synthetic/VM-тестов).
- [ ] macOS: позиционирован как ограниченный/ручной сенсор; продакшн-survey
      отказывает на ассоциированном адаптере (текущее поведение сохранено).
- [ ] Android: offline-верификатор/просмотрщик подтверждён на реальном устройстве;
      замечание по контрасту статус-бара (dark) закрыто или задокументировано.
- [ ] Зависимости (tcpdump/`iw`/CoreWLAN helper) проверяются сенсором при старте и
      отражаются в health-статусе backend.
- [ ] SLA EASM не обещает покрытие драйверов/радио сверх пройденной приёмки.

## Сквозные принципы (во всех этапах)
- Исходный код `aircrack-rs` в рамках интеграции не меняется сверх согласованных
  отдельных изменений (exit codes/JSON — этап 1 как будущая работа).
- Модуль остаётся пассивным: без инъекции/деаутентификации/fake AP/WEP-SAE recovery.
- Авторизация владельца сети обязательна до любого радио-действия.
- Секреты (пароли/PMK/PCAP payload) не покидают доверенный периметр верификации.
- Все bounded-лимиты существующего кода сохраняются и не ослабляются.
